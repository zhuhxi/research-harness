# 每周研究交接

目标不是"一份短报告"，而是让读者**读完能独立解释、能回答导师追问**。所以每个结论都要带证据链接，并附自测题。

## 取材（只用文件与 git，不凭记忆）
- 本周期范围：上一份 `logs/交接/` 之后的所有提交（没有就取全部）
- `goal.yaml`、`research-state.yaml`、`findings.md`
- 期间所有 `hypotheses/H*/protocol.md`、`result.md`、结果 JSON、关键代码 diff（`git diff <起点>..HEAD -- src/ hypotheses/`）
- `logs/简报/` 本周各份简报、`logs/实验记录.jsonl`、`logs/作业.jsonl`
- **数字必须重新从结果 JSON 读一遍核对**，与 result.md 不一致时如实写出不一致。

## 结构（按顺序；总篇幅以 1 小时读完为准，约 3–5 页）

### 0. 阅读路线（放最前）
- 推荐阅读顺序与预计时间，例如："先读第 1 节（10 分钟）→ 打开 H07/result.md 和图 X（15 分钟）→ ……"
- 必看的 3–5 个文件路径

### 1. 本周一句话 + 三个要点
- 一句话结论（带数字）
- 三个要点：最重要的进展、最重要的失败、最大的不确定性

### 2. 核心假设与结论
| 编号 | 假设（一句话） | 类别 | 阶段 | 判定 | 关键数字（均值±标准差，n） | 证据 |
|---|---|---|---|---|---|---|
- 只列本周有判定的假设；按重要性排序，不按编号

### 3. 关键改动及科学动机
- 每个改动：改了什么（指向代码文件与提交号）→ 为什么可能有效（机制）→ 证据支持到什么程度
- 用读者能复述的话写机制，不堆术语

### 4. 证据链
- 主张 → 实验 → 结果文件 → 图，逐条可点开
- 对照是否公平（同数据、同预算、同种子数）明确写出

### 5. 失败方向（同样重要）
- 试过什么、为什么失败、排除了哪些解释；以后不要再试的写明

### 6. 未解决问题、潜在错误与不确定性
- 可能的 bug、数据泄露风险、种子方差大、只在 toy 上成立、未预注册的观察等
- 每条写"怎样验证"

### 7. 导师可能追问（5–8 个）
- 每个问题：简短回答 + 可验证依据（文件路径/数字）。答不了的写"目前无法回答，需要做 X"

### 8. 下周最值得做的方向（≤3 个）
- 每个：预期收益、成本（toy/pilot/full、GPU 小时）、失败了说明什么
- 需要 Director 决定的事单独列出：research-state.yaml 的 pending_approvals 逐条（事项、理由、证据），以及停机请求

### 9. 自测题（5–8 题）
- 覆盖：核心结论与数字、机制解释、对照公平性、失败原因、最大风险
- 题目在前，答案放在文末"自测答案"一节，每个答案附证据路径
- 读者答得上来，才算真正理解；答不上的题目对应的部分需要重读

## 规则
- 核对数字用 Read 工具直接读结果 JSON 和 result.md，不依赖 shell；不得以"shell 被拒"为由跳过核对。
- 开头注明"截至第 X 轮、提交号 Y"，读者能判断是否过时。
- 不编造数字、引用、机制；证据不足就写"证据不足"
- 结论强度与证据匹配："存疑"不写成"有效"，toy 结果不写成定论
- 写作简洁直白，避免空洞套话和夸张形容词
- 写完 `git add logs/交接/ && git commit -m "研究交接 YYYY-MM-DD"`
